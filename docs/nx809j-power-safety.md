## Battery and PMIC GLINK: keep XEC battmgr out

The XEC `qcom_battmgr` driver has an unsafe NX binding path. Its probe selects a variant from the parent compatible table, but an unmatched parent falls back to `QCOM_BATTMGR_SM8350`; this is not a rejection or an Oplus-path gate. The Oplus behavior runs later, after PMIC GLINK reports the SoCCP service up and the notification request succeeds:

| Call path | Source behavior |
|---|---|
| `qcom_battmgr_pdr_notify()` → `enable_work` | Service-up schedules the work. `qcom_battmgr_enable_worker()` requests notifications, then calls `qcom_battmgr_oplus_gauge_init()` without a variant check and schedules `otg_init_work` after 3.5 seconds. [`qcom_battmgr.c` lines 2652–2698](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/power/supply/qcom_battmgr.c#L2652-L2698) |
| Oplus gauge initialization | It attempts `BATT_OPLUS_ADSP_GAUGE_INIT=1`; on success it attempts `USB_OPLUS_VOOCPHY_ENABLE=1`, then dummy `BATT_OPLUS_RTC_SOC=50` and `BATT_OPLUS_UPDATE_SOC_SMOOTH_PARAM=1`. It later configures charger limits and schedules a periodic Oplus recheck. [`qcom_battmgr.c` lines 2210–2286](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/power/supply/qcom_battmgr.c#L2210-L2286) |
| Delayed OTG setup | The queued worker waits 10 seconds, then sends `USB_OTG_AP_ENABLE=true`. Because it is scheduled after successful notification registration regardless of whether gauge initialization succeeds, it is a separate unguarded request. [`qcom_battmgr.c` lines 2703–2719](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/power/supply/qcom_battmgr.c#L2703-L2719) |
| VOOC and current policy | Notifications can schedule VOOC status/recheck work. If the USB supply is online and not marked OTG, the recheck can request PDO, input-current, charge-enable, VoocPHY and FCC changes; DCP selects a 7.3 A ICL request. This path is conditional on subsequent state/events, unlike the initial gauge/OTG work. [`qcom_battmgr.c` lines 1636–1735 and 2313–2433](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/power/supply/qcom_battmgr.c#L1636-L1735) |

The `of_match` table chooses a variant but does not guard these Oplus calls. XEC's `pmic_glink_soccp_data` enables BATT, altmode, and UCSI clients; the parent driver creates an auxiliary `power-supply` device from that mask. The battery auxiliary can therefore be exposed by a supported Kaanapali PMIC-GLINK parent even if the FDT's `battery-charger` child is marked disabled. The robust probe gate is to compile `BATTERY_QCOM_BATTMGR` out, not to rely on that child status. See [`pmic_glink.c`](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/soc/qcom/pmic_glink.c#L183-L205) and [its SoCCP client mask](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/soc/qcom/pmic_glink.c#L407-L435).

The saved NX FDT parent compatible is `qcom,qti-pmic-glink` on `PMIC_RTR_SOCCP_APPS`. XEC's provider does not match that compatible; it matches `qcom,kaanapali-pmic-glink` for the generic SoCCP client set. The current NX review DTS adds no PMIC-GLINK or battery nodes, so it currently cannot bind this path. If PMIC GLINK is added later for UCSI, use a source-reviewed SoCCP provider mapping and keep the battery driver disabled before exposing its auxiliary device.

UCSI has a separate Kconfig driver and can remain available independently of battmgr: `UCSI_PMIC_GLINK` depends on `QCOM_PMIC_GLINK`. This is defensible at the code/configuration layer, but the NX node shape is not yet compatible. XEC's provider attaches the auxiliary device to the PMIC-GLINK parent node; `ucsi_glink.c` iterates that node's direct children and returns an error if any child lacks `reg`. XEC puts `connector@0` directly below `pmic-glink`; NX nests `connector` below a `ucsi-glink` child, while its direct `battery-charger` and `ucsi-glink` children lack `reg`. The NX tree must use a Linux-specific, direct-child connector description (and omit the unsupported vendor wrappers) checked against the phone's actual port/DP wiring before claiming UCSI works. [`ucsi_glink.c` lines 394–466](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/usb/typec/ucsi/ucsi_glink.c#L394-L466)

The recorded XEC build config has `CONFIG_BATTERY_QCOM_BATTMGR=m`, `CONFIG_QCOM_PMIC_GLINK=y`, and `CONFIG_UCSI_PMIC_GLINK=y`; the upstream Linux 7.3 reference config has battmgr, PMIC GLINK and UCSI as modules. There is no NX-specific kernel config yet. If either reference config is reused and the PMIC-GLINK parent becomes bindable, the battery module must be excluded explicitly. The one-line review-only override is [nx809j-no-battmgr.fragment](../artifacts/power-safety/nx809j-no-battmgr.fragment). It preserves whatever GLINK/UCSI configuration the chosen base already provides. It does **not** prove Linux can charge the phone: SoCCP charging behavior with battmgr absent is unknown.

## Thermal trips and what they mean

The Android FDT has many vendor thermal zones and cooling maps. Its `reset-mon-cfg` entries at 125 °C are typed `hot`; that name does not make them standard Linux critical trips or prove a TSENS hardware-reset action. The XEC TSENS ops expose `get_temp` and `set_trips`, not `.hot`. In the thermal core, a hot trip calls `.hot` only if provided; critical trips call `.critical`, which defaults to the critical handler. [`tsens.c` lines 1226–1229](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/thermal/qcom/tsens.c#L1226-L1229), [`thermal_core.c` lines 345–353 and 1485–1487](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/thermal/thermal_core.c#L345-L353).

The current NX candidate includes XEC's Kaanapali SoC DTS. That DTS already supplies 120 °C `hot` and 125 °C `critical` trips on TSENS channels, including `gpuss-0` (`tsens5 0`). No duplicate NX trip is needed for that source-derived definition. The Kaanapali SoC DTS has no `cooling-maps`, however, so its CPU/GPU zones do not gain passive throttling from those trip entries. The critical path calls `__hw_protection_trigger()` and then `orderly_poweroff(true)`. The reference XEC config sets `THERMAL_EMERGENCY_POWEROFF_DELAY_MS=0`, which skips the delayed forced fallback; actual shutdown on NX has not been tested. [`kaanapali.dtsi` GPU zone](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/arch/arm64/boot/dts/qcom/kaanapali.dtsi#L7511-L7527), [`thermal_core.c`](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/drivers/thermal/thermal_core.c#L314-L353), [`reboot.c`](https://github.com/Xlie-Electronic-Customs/linux/blob/6d6be0ba139e89d843e62f56cbd9f829775901d5/kernel/reboot.c#L1004-L1053).

The Android capture includes 12 `qcom,spmi-temp-alarm` nodes and critical PMIC-temperature trips. XEC has a compatible driver that configures thresholds from registered trips and writes `ALARM_CTRL_FORCE_ENABLE` during probe. That is evidence of a driver-programmed hardware protection mechanism **if** the correct PMIC instance, trip data, regmap and driver all bind. The NX review DTS does not yet add those PMIC temperature-alarm nodes. The capture does not show the alarm registers' active settings, so it is not evidence that the PMIC currently has those thresholds armed under Linux. [`qcom-spmi-temp-alarm.c` threshold/programming path](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/thermal/qcom/qcom-spmi-temp-alarm.c#L309-L376), [probe and always-on enable](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/thermal/qcom/qcom-spmi-temp-alarm.c#L739-L885).

Likewise, the presence of a SoCCP remoteproc, firmware names, and a PMIC-GLINK channel proves an interface exists in the Android FDT. It does not prove the battery, fuel-gauge, JEITA, or current-limit policy runs independently of Linux or that it remains safe when the GLINK battery client is absent. The T-004 row note that battery management “runs on ADSP firmware” is not sufficient as evidence for those behaviors. Treat charging autonomy and PMIC/TSENS armed state as unresolved, not confirmed fallback layers.

## Current candidate status and remaining safety gaps

The current review DTS patch only enables the evidenced SPI/touch resources and defines its touch rails. It does not add PMIC GLINK, `battery-charger`, UCSI, PMIC temperature alarms, ADC thermistors, a fan, or vendor cooling devices. It inherits generic Kaanapali TSENS trip definitions through the SoC include. The XEC reference config enables TSENS and the PMIC temperature-alarm driver, but a config option alone cannot activate absent device-tree nodes.

Important limits before sustained load:

- **No supported ADC gen4 path:** NX declares `qcom,spmi-adc5-gen4`; XEC has only the gen3 driver, which is disabled in its recorded build config. Skin, battery and USB thermistor readings are not established.
- **No fan driver/control:** NX's `soc,fan` is not implemented in XEC. The fan has no thermal cooling-cell/map binding. Its PMH0101 L8 rail is also used for SD-card VDD-IO voltage switching; do not enable SDCC2 until that interaction is resolved.
- **No thermal throttling map:** the XEC Kaanapali DTS has zero `cooling-maps`. The vendor Android maps use cooling devices with no upstream driver.
- **Watchdog is unresolved:** NX's vendor node uses `qcom,msm-watchdog` with two level-triggered interrupts; XEC Kaanapali uses a different compatible/interrupt description. The XEC reference config builds `QCOM_WDT=m`, not an early, tested watchdog path.
- **No evidenced charging policy:** do not send XEC Oplus property IDs or current/PDO requests to the NX SoCCP. No property-unit or protocol behavior is inferred here; a separate source review must establish those before a Linux battery-control implementation.

## Review-only initial config gate

`CONFIG_BATTERY_QCOM_BATTMGR` depends on `QCOM_PMIC_GLINK`; it is separate from `UCSI_PMIC_GLINK`. For the initial NX config, exclude the battery manager while preserving the base's PMIC-GLINK/UCSI choices. The fragment is review-only and has not been merged or built. It does not add a PMIC-GLINK node, enable UCSI on the phone, or claim charging works.

The exact source/config/FDT hashes are in [source-hashes.sha256](../artifacts/power-safety/source-hashes.sha256), and the proposed gate is [nx809j-no-battmgr.fragment](../artifacts/power-safety/nx809j-no-battmgr.fragment). The independent review used the raw T-008 result at [T-008.stdout.json](../artifacts/claude-mapping/T-008.stdout.json) and the imported [power/thermal map](../collab/results/T-008-power-thermal-map.md). No production source or existing DTS patch was changed; no build or phone test was performed.
