# NX809J GPU ID and Mesa 26.1.6 applicability

Reviewed 2026-10-19. This is a source and package review only. The phone GPU, its firmware, and the Mesa drivers have not been run under Linux.

## Finding

The frozen Mesa 26.1.6 source contains an A840 device-info entry, but the NX809J FDT ID does **not** match that entry as-is. It becomes an exact Mesa match only if the pinned mainline A8xx driver successfully reads all three active slices and exports the resulting runtime chip ID. Separately, the compatible string reported for the NX GPU is not accepted by the pinned mainline DRM MSM OF match table or binding unless a supported fallback compatible is also present.

| Evidence | Identifier or label | What it establishes |
|---|---|---|
| T-004 captured FDT report | `qcom,chipid = 0x44050a01`; label `Adreno840v2` | NX809J-reported base chip ID and vendor label |
| Linux 7.3 A840 catalog | `0x44050a01`, `ADRENO_8XX_GEN2`, `max_slices = 3` | Mainline has an A840-family catalog entry for the same base ID |
| Linux 7.3 runtime chip ID | `0x44050a31` if three slices are active | A8xx adds the active-slice count into bits 7:4 before exporting `MSM_PARAM_CHIP_ID` |
| Mesa 26.1.6 table | `0x0000ffff44050a31`, name `Adreno (TM) 840` | Mesa matches the runtime chip ID while treating bits 47:32 as fuse/speedbin wildcard |

The final byte `0x31` is not simply a new marketing name or a generic A840 family match: the kernel’s ID construction combines the base low nibble `1` with the active-slice count `3` in bits 7:4. The Mesa source compares numeric IDs, not the strings `Adreno840v2` or `Adreno (TM) 840`. If only the unmodified base `0x44050a01` reaches Mesa, or if the GPU exposes fewer than three slices, this exact A840 table row does not match. The static arithmetic check records that conditional result in [chip-id-check.json](../artifacts/gpu-id-analysis/chip-id-check.json).

There is a more basic kernel gap in the current board candidate: the pinned Kaanapali SoC DTSI has GPU clock-controller data and a GPU microcode-memory reservation, but no Adreno `gpu@` platform node. The Kaanapali MTP DTS and current NX809J review patch also add no GPU node. Without one, DRM MSM has no GPU device to probe, so the chip-ID path above is conditional future work. The bounded file scan and source hashes are included in [source-evidence.txt](../artifacts/gpu-id-analysis/source-evidence.txt).

## Source path

The frozen Debian source package is `mesa 26.1.6-1~bpo13+1`, from the `20261019T000000Z` Trixie backports snapshot. Its `freedreno_devices.py` entry sets `chip_id=0xffff44050A31`, labels the device A840, and supplies A8XX properties with three slices. The matching code in `freedreno_dev_info.c` uses the chip ID because that table row has no legacy GPU ID. Its fuse wildcard fills bits 47:32, then still requires the lower chip/slice ID to match. [The upstream A840 device-info change](https://gitlab.freedesktop.org/mesa/mesa/-/commit/6e3598177b8ed02f06ebbeeaca865b7cfcbbe87b) is present in this exact source package. Debian applies only `path_max.diff` (two test files) and `src_glx_dri_common.h.diff`; neither patch touches Freedreno device matching.

The mainline path is also concrete in the pinned Linux source. `a6xx_catalog.c` associates base ID `0x44050a01` with A8xx Gen 2 and three maximum slices. `a8xx_gpu_get_slice_info()` reads the active-slice register and adds the count to the chip ID; GMU initialization calls it before starting the GMU firmware. The DRM `MSM_PARAM_CHIP_ID` query returns that updated value. Mesa’s MSM pipe queries the DRM parameter and passes it through its device table lookup. See the [pinned A840 catalog](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/gpu/drm/msm/adreno/a6xx_catalog.c#L2443-L2484), [slice-ID adjustment](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/gpu/drm/msm/adreno/a8xx_gpu.c#L85-L121), and [DRM chip-ID export](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/gpu/drm/msm/adreno/adreno_gpu.c#L389-L394), plus the saved [source excerpts and hashes](../artifacts/gpu-id-analysis/source-evidence.txt), [source provenance](../artifacts/gpu-id-analysis/debian-source-evidence.txt), and the [reproducible excerpt capture](../artifacts/gpu-id-analysis/capture_source_evidence.py).

The captured compatible is reported as `qcom,adreno-gpu-gen8-2-1`. In pinned Linux, the Adreno OF match includes `qcom,adreno` and the generic binding accepts `qcom,adreno-<8 lowercase hex digits>` followed by `qcom,adreno`; it does not list `qcom,adreno-gpu-gen8-2-1`. If the captured string is the node’s only compatible, the mainline driver will not match it. A mainline DT port should verify the full compatible array and use a binding-supported form, such as `qcom,adreno-44050a01` with the `qcom,adreno` fallback, before claiming the GPU can probe. This is a DT compatibility requirement, not a Mesa package issue. [Pinned kernel OF table](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/gpu/drm/msm/adreno/adreno_device.c#L296-L303) · [Pinned GPU binding](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/Documentation/devicetree/bindings/display/msm/gpu.yaml#L25-L45)

## Debian ARM64 package support

The exact Debian source index lists the Mesa source package as `Architecture: any`, has ARM64-specific build dependencies, and publishes `mesa-vulkan-drivers` for `arm64`. The frozen rootfs artifact contains Mesa `26.1.6-1~bpo13+1` packages for ARM64. Its package manifest and dependency metadata record the archive/package provenance. The builder installs those Debian ARM64 binaries; it does not compile Mesa. It checks that the resolved Mesa packages are arm64 and validates that `msm_dri.so` and `libvulkan_freedreno.so` are AArch64 ELF files.

This proves the selected userspace has an ARM64 package path and an A840 device-info row. It does not prove that the NX809J kernel exposes the required DRM interface, that the GPU initializes, or that graphics render correctly.

## Firmware and remaining GPU gates

The pinned A840 kernel catalog requests `gen80200_sqe.fw`, `gen80200_gmu.bin`, and `gen80200_aqe.fw`. T-004 records filename associations for these `gen80200` files in the Android-side material, but the actual file bytes, hashes, and availability through Linux’s firmware lookup paths were not verified. Mainline first tries `qcom/<name>`, then the legacy root path, then the firmware helper. The current Debian/Mesa rootfs has no vendor firmware. The A840 catalog entry does not declare a `.zapfw` filename; A8xx init has an optional ZAP path and a SECVID fallback. Review the NX809J `zap-shader`/secure-world DT state before declaring that path resolved. [Pinned A8xx secure-mode path](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/gpu/drm/msm/adreno/a8xx_gpu.c#L786-L810)

Before calling the GPU supported, validate a mainline-compatible GPU node and its clocks, regulators, interconnects, GMU relationship, IOMMU, and power domains; establish that the slice probe returns three active slices; package and hash the exact compatible firmware files; then record `MSM_PARAM_CHIP_ID` and the Mesa device selection during a real render test. Until then, Mesa 26.1.6 is a **conditional userspace match**, not verified NX809J acceleration.
