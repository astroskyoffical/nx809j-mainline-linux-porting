# Compressed root storage options

The exact Debian 13 + Mesa 26.1.6 + Denial root filesystem is **not ruled out by the raw gap size**. Its existing `.tar.zst` archive is 381,761,729 bytes, 592,065 bytes larger than the reported `sde` GPT gap; repackaging the filesystem as XZ SquashFS produces a 340,762,624-byte image. This is only a byte-count fit; it does not authorize or validate a partition change.

| Option | Measured size | Comparison | What it establishes |
|---|---:|---:|---|
| Full root in RAM as `newc` initramfs compressed with XZ | 266,474,504 B | + reference Linux `Image` (41,851,392 B) and reference Kaanapali DTB (182,658 B) = 308,508,554 B; 496,797,814 B below the reported 805,306,368 B fastboot download limit | The size envelope looks plausible. The final NX809J kernel, DT, boot container/header/alignment, available RAM, and whether `fastboot boot` accepts the image are untested. The expanded tree alone is 1,239,047,234 B (~1.154 GiB), before runtime services and caches. RAM-root changes are lost on reboot unless user data is written elsewhere. The `newc` size stream was discarded; it does not preserve the source ACL xattrs. No initramfs or boot image was built. |
| Read-only XZ SquashFS | 340,762,624 B (324.98 MiB) | The captured gap is 381,169,664 B (363.51 MiB), leaving 40,407,040 B (38.54 MiB) by subtraction | The filesystem image fits numerically. Actual partitionability, alignment, OTA safety, device accessibility, and Linux UFS support remain unproven. It supplies no writable state; an overlay or separate writable storage is still required. |

## SquashFS artifact and checks

The [SquashFS image](../artifacts/root-storage-fit/debian13-arm64-mesa26.1.6-denial-20261019T203758Z-13-root.squashfs) uses SquashFS 4.0, XZ compression, 128 KiB data blocks, and four build workers. SHA-256 is `6fd378dd4e62362c415025297d0f8025e14b21a01936c931404dd8d2c57025ea`. The [superblock](../artifacts/root-storage-fit/superblock.txt), full numeric-ownership [filesystem listing](../artifacts/root-storage-fit/listing.txt), [extraction log](../artifacts/root-storage-fit/unsquashfs-extract.log), [validation record](../artifacts/root-storage-fit/validation.txt), and [manifest](../artifacts/root-storage-fit/manifest.json) are stored alongside it. `unsquashfs` extracted all files successfully. The source and extracted trees had the same normalized path/type/mode/UID/GID/symlink-target hash; file data was read and decompressed by the full extraction. The hash deliberately excludes extended attributes and timestamps.

There is one metadata limitation in both size prototypes: the source tree had `system.posix_acl_access` and `system.posix_acl_default` on `/var/log/journal`. `mksquashfs` warned that those prefixes are unrecognized; the image has no xattr IDs. `newc` does not carry those xattrs either. SquashFS’s kernel documentation says POSIX ACL support is unavailable, so the ACLs are not preserved by this format. No other source extended attributes were present. If either root is used, test whether writable provisioning and systemd tmpfiles restore the required journal ACLs. [Linux SquashFS documentation](https://docs.kernel.org/filesystems/squashfs.html)

## Kernel and boot requirements

For the direct SquashFS root, build SquashFS and XZ decoding into the kernel (`CONFIG_SQUASHFS=y`, `CONFIG_SQUASHFS_XZ=y`); the root filesystem cannot be supplied as a module. The kernel also needs a built-in block and storage-controller path to whichever medium holds the root. If the image is a file on another filesystem, the initramfs must bring up that filesystem and storage path first. Any mutable `/etc`, `/var`, package updates, and user data need a separate writable overlay or data store.

For the RAM-root measurement, the boot path needs initramfs support (`CONFIG_BLK_DEV_INITRD=y`) and XZ initrd decompression (`CONFIG_RD_XZ=y`). The running system then needs enough RAM for the expanded 1.154 GiB root tree, services, application memory, and page cache. A read-only SquashFS does not have to be configured for this RAM-root option.

The boot-loader and fastboot facts are from the read-only October 19 device capture summarized in [recovery.md](recovery.md); fastboot’s 805,306,368-byte reported transfer maximum does not prove a Linux image is accepted. The GPT gap figure is from the same captured partition analysis summarized in [plan.md](plan.md). The source rootfs also still has a locked root account and no provisioned interactive user, so it is not yet ready to launch a Denial session. No partition geometry was altered, no boot image assembled, and no phone operation was performed for this study. The reference kernel and DTB sizes are host build outputs, not NX809J phone images.
