# NX809J boot-chain findings

Reviewed 2026-10-19 from the phone's saved readbacks and the project's August–October XDA archive. This note answers what the available evidence says about the engineering `userdebug` build, Fastboot entry, and whether the current boot path can temporarily boot Linux. No firmware was executed and no phone operation was performed for this analysis.

## Current phone and saved firmware evidence

The authorized read-only USB check already reached bootloader Fastboot on this phone. It reported `product:canoe`, `unlocked:yes`, `secure:yes`, `is-userspace:no`, current slot A, and two slots; Android then returned to the verified A path. This proves that Fastboot entry is available now. It does not prove that `fastboot flash`, `fastboot boot`, Linux image verification, or inactive-slot boot will work. Neither write/boot command has been tested. See [recovery and storage boundaries](recovery.md) for the device-level state and recovery gate.

The saved ABL A and B images are each 1 MiB, ELF32 little-endian ARM executables with entry address `0x9fa00000`; they are byte-identical to one another (`e6ae2a6c08abc3dde5430cf93a06a606ce208a570e69b1a9c4c7625592045e6d`). This establishes equality of the two captured ABLs, not that they are stock, engineering, signed for a particular build, or interchangeable with another handset. The available REA/Ghidra provider does not support this ARM ELF profile, so their code was not decompiled. The limitation is recorded rather than treating the ABL as empty.

The saved `efisp.img` is a 3 MiB PE/ARM64 image (SHA-256 `4df183594a63af28c681e48b1d9fdb0305ee055ea8fde92118a1e0af7a5f6f17`). Ghidra 12.1.4 mapped PE headers and sections through image address `0x31000`; the bytes beyond that mapped range were not analyzed. The image references `LinuxLoader.dll` debug information, but its PDB GUID/signature are unknown and no PDB was loaded. Its recorded PDB path includes `gbl_root_canoe/.../LinuxLoader.c`; this is a provenance clue only, not proof that the image was built from that repository revision.

Radare2 6.2.4 independently reports PE preferred image base `0x10000`; `.text`, `.data`, and `.reloc` have raw offsets `0x1000`, `0x18000`, and `0x30000`, and preferred VAs `0x11000`, `0x28000`, and `0x40000`. For these mapped sections the PE RVA equals the file offset, and the preferred VA is `0x10000 + file offset`. Thus the callback is Ghidra address/file offset/RVA `0xC93C`, R2 preferred VA `0x1C93C`; the Fastboot error string at file offset `0x151A9` is R2 VA `0x251A9`. These are preferred analysis addresses, not observed runtime load addresses. Raw section and entrypoint records are in `artifacts/boot-analysis/rabin2-sections.json` and `rabin2-entrypoints.json`.

## Fastboot entry and command evidence

In the saved PE, `FUN_00007734` checks the volume-down key and includes a five-second Fastboot prompt; the code then calls a Fastboot routine. The Fastboot initializer (Ghidra address/file offset `0xB1E4`, R2 preferred VA `0x1B1E4`) and its command table (file offset `0x18318`, R2 preferred VA `0x28318`) contain entries for `flash:`, `erase:`, `set_active`, `flashing unlock`, `flashing lock`, `boot`, `download:`, `getvar:`, and reboot commands. These are static binary observations: a command name and callback pointer in the image do not prove that the current phone entered this exact path, accepts the command, or can safely write the named target. The current read-only USB session did not exercise write commands.

The `boot` table entry points to code at file offset/RVA `0xC93C` (R2 preferred VA `0x1C93C`). Ghidra decoded the first instruction but did not create a function body; a bounded radare2 disassembly of the callback resolved its input contract:

- It rejects sizes below `0x660`, then checks the eight-byte `ANDROID!` magic at the start of the Fastboot data. The magic is at file offset `0x14DCB` (R2 VA `0x24DCB`).
- It reads the boot header's `header_version` at offset `0x28`; versions above 2 use a fixed kernel offset of `0x1000`, while older versions use `page_size` at offset `0x24`. It reads `kernel_size` at offset `0x08`, rejects zero or out-of-bounds values, and checks that the kernel payload at the computed offset begins with PE/COFF `MZ` bytes.
- For a match it announces `Booting EFI image...` (file offset `0x14443`, R2 VA `0x24443`), stops the Fastboot USB path, passes only the kernel payload and `kernel_size` to UEFI `LoadImage` (Boot Services table offset `0xC8`), then calls `StartImage` (offset `0xD0`). For a mismatch it passes `No EFI image found in boot.img` (file offset `0x151A9`, R2 VA `0x251A9`) to the failure path.

This means the current EFISP `boot` callback does **not** accept a raw `.efi` or raw Linux `Image` as its command payload: it expects an Android boot-image wrapper whose `kernel` field starts with a UEFI-loadable PE image. The initial `MZ` test is only a signature check; actual PE loading and any policy enforcement are delegated to UEFI `LoadImage`. This callback only forwards the kernel bytes; it does not pass the Android boot image's ramdisk, command line, or other header fields to `StartImage`. A Linux EFI stub could be a candidate for the inner payload, but the initramfs/root, device-tree, command-line, secure-image policy, and kernel handoff requirements remain unresolved. The helper names are inferred; the disassembly and byte offsets are retained in `artifacts/boot-analysis/r2-callback-entry.txt`, `r2-callback-handoff.txt`, and `r2-no-efi-xref.txt`.

Two separate loader helpers at Ghidra offsets `0xDB9C` and `0xDE14` still lack recovered source names: the first reads and validates a range, checks a `boot` string, and calls the second; the second builds a `boot`-prefixed lookup path and edits records. This is consistent with boot-entry lookup but does not identify the partition or filesystem. The saved `persist.img` root has no `/efisp` directory at that exact path; this bounded directory check does not rule out another path or a raw-partition lookup.

The pinned [`gbl_root_canoe` source at `e3f935c4db212495c9eac219cee6f6badea65641`](https://github.com/superturtlee/gbl_root_canoe/tree/e3f935c4db212495c9eac219cee6f6badea65641) independently implements the same `ANDROID!`/page-size/kernel-size/`MZ` checks, then calls `LoadImage` and `StartImage`. This is a strong behavioral match for the callback, but does not prove the entire saved PE came from that exact revision. The repo's README says `fastboot boot xxx.efi`, which conflicts with its own `CmdBoot` implementation: a raw `.efi` does not satisfy the code's Android-header check. The pinned `LinuxLoader.c` also uses a Volume-Up boot menu, unlike the saved PE's Volume-Down prompt. See [`FastbootCmds.c`](https://github.com/superturtlee/gbl_root_canoe/blob/e3f935c4db212495c9eac219cee6f6badea65641/submodules/uefi/edk2/QcomModulePkg/Library/FastbootLib/FastbootCmds.c), [`LinuxLoader.c`](https://github.com/superturtlee/gbl_root_canoe/blob/e3f935c4db212495c9eac219cee6f6badea65641/submodules/uefi/edk2/QcomModulePkg/Application/LinuxLoader/LinuxLoader.c), and the conflicting [README instruction](https://github.com/superturtlee/gbl_root_canoe/blob/e3f935c4db212495c9eac219cee6f6badea65641/README.md).

## Fastboot state labels and write capability

The `secure` and `unlocked` variables are not hard-coded `yes` strings. In the saved PE's publisher, `secure` selects `yes` or `no` from a helper result (`FUN_00011B08`); `unlocked` does the same from `FUN_00011D48`. The `yes` and `no` text constants are at file offsets `0x151A5` and `0x15E09`. The `secure` helper obtains an interface and calls an indirect method at interface offset `+0x38`; that interface is unresolved. The `unlocked` helper reads a state byte at preferred VA `0x3EF25` (file offset `0x2EF25`) after a global-pointer check; a separate critical-state helper reads `0x3EF26`. Those bytes are zero in the saved PE's initial data image, but runtime initialization and their state semantics were not resolved. The current USB `unlocked:yes` result describes the Fastboot implementation's reported state; it does not prove an unlock-ability flag, a hardware fuse state, a stock ABL, or acceptance of any write.

`flashing get_unlock_ability` is separate. Its callback at file offset `0xC850` reads global `DAT_0002081C` (R2 preferred VA `0x3081C`) and formats that value. The data image initially contains zero there. The focused [ability-flag analysis](nx809j-efi-permission-gate.md) now identifies Fastboot initialization calling a reader keyed `frp`; on a successful indirect read it stores the final record byte masked with 1 through the global output pointer. The backing record provider, persistent-store semantics and current runtime value remain unresolved; a failed read leaves the initial zero unchanged. The normal and critical `flashing unlock` callbacks route through a shared state handler: the wrapper passes `(critical=0, unlock=1)` or `(critical=1, unlock=1)`. That handler checks the current normal/critical state and, when an unlock is requested, denies it if `DAT_0002081C == 0`, using the exact error `Flashing Unlock is not allowed`. Lock requests use `unlock=0` and do not take that ability-denial branch. The critical command changes a separate lock state; its presence does not establish per-partition protection.

A Fastboot transfer/dispatch path at file offset `0xBBC4` calls a helper that also checks `DAT_0002081C`; its failure route references `Flashing is locked` and aborts before the later command-dispatch jump. This establishes a gate on the observed helper routes, including some download/flash dispatch paths. Command-table registration occurs independently of the flag, and neither the analyzed `boot` callback nor the registered `flash:` callback has a direct flag read in that slice. Exact upload/dispatch coverage is unresolved, so this is not an independent blanket flash-authorization rule or a proven direct `CmdBoot` gate. The phone's current flag value and actual command acceptance remain unknown; `unlocked:yes` does not settle them.

The `flash:` callback is present in the saved PE's command table. The pinned source's `ENABLE_UPDATE_PARTITIONS_CMDS` guards command registration; its `CmdFlash` accepts a partition name/LUN, looks up the partition, checks image/partition bounds, handles raw/sparse/UBI/meta image formats, and calls partition-write helpers. That source body contains no `boot`/`init_boot`/`vendor_boot` deny list, critical-partition test, AVB verification, or image-signature check. The saved binary's callback and table agree that a generic flash handler exists, but the source revision is not proven to be the exact binary source. The inspected callback/source slices contain no target-specific rule for those three partition families; behavior in other firmware layers remains unknown. Treat their acceptance as unknown; do not attempt a write. `secure:yes` is not evidence that Fastboot verifies an image before writing or that the next boot will accept it. See the pinned [`CmdFlash` implementation](https://github.com/superturtlee/gbl_root_canoe/blob/e3f935c4db212495c9eac219cee6f6badea65641/submodules/uefi/edk2/QcomModulePkg/Library/FastbootLib/FastbootCmds.c#L1540-L1750).

The captured ABL A/B hashes do not match the public [Canoe Dock `abl_unlock.elf`](https://github.com/Coding-BR/rm11pro-canoe-dock/blob/27177301b45ae9cb3d9271b9f53aa1ae6be5ff77/abl_unlock.elf) or any of the 11 ABL hashes tracked by the pinned `gbl_root_canoe` repository. This is a bounded comparison against those references; it does not identify the captured ABL's originating build. The comparison hashes and source revisions are in the private [boot-analysis index](../artifacts/boot-analysis/source-index.json).

## Decision and remaining unknowns

- Do not install the XDA userdebug ROM just to enter Fastboot; the current phone already reaches it. The reason to pursue that ROM in the community discussion was broader development/debugging functionality, not basic Fastboot entry.
- The saved EFISP has a compiled `flash:` handler and an unlock-ability gate. This does not prove the current USB Fastboot session uses this exact image or accepts `flash:`. A full userdebug ROM is not established as necessary solely to expose the code or enter Fastboot; do not replace the Android installation just to test a label.
- Do not transplant an engineering ABL or attempt the XDA EDL/GSI sequence. Its compatibility with this exact handset and firmware is unverified, and the same thread documents a device-specific ABL failure.
- `flash:` and `boot` entries in the EFISP image are not a permission or safety check. Do not treat them as authorization to write or boot an image.
- Keep Android A unchanged. Before any future temporary Linux boot, complete the project recovery gate and resolve the UEFI initramfs/device-tree/cmdline path, image policy, and return route. A plausible offline candidate format is an Android boot wrapper with an EFI-stub PE in its kernel field; it has not been built or tested.
- `fastboot boot` remains untested. The evidence does not establish whether the current USB Fastboot session entered through this EFISP binary, what role `secure:yes` plays in this handset's policy, what checks the unreadable ABL performs, or whether UEFI `LoadImage` will accept a particular Linux build.
