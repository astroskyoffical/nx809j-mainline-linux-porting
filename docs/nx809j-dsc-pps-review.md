# NX809J DSC/PPS independent review

**Result:** T-013's numerical comparison reproduces from the pinned vendor and mainline sources. With the captured 1216×2688, 608×16, 10-bpc, 8-bpp profile, the two generated 128-byte PPS buffers differ only at byte 58: vendor `0x02`, mainline `0x01`. That is the only computed PPS-byte mismatch for these inputs. It is not evidence that this is the only blocker to a working display, or that either profile is accepted by the panel.

## What the comparison establishes

Vendor `sde_dsc_populate_dsc_config()` selects its 1.1, 10-bpc, 8-bpp row and writes range 0 maximum QP 8 (`sde_dsc_helper.c:67-70,301-315`). Mainline selects its 1.1 pre-SCR row; its source comment distinguishes the model's range-0 value 8 from VESA DSC 1.1 Table E-5's value 4 (`drm_dsc_helper.c:379-389`). The other fourteen rate-control ranges and the other derived values match in the rebuilt configuration.

The PPS packing code makes the byte difference explicit. Vendor packs `range_max_qp >> 2` into the high portion of PPS byte 58 (`sde_dsc_helper.c:592-601`); mainline packs the same range field into PPS bytes 58–59 (`drm_dsc_helper.c:241-253`). With range-0 min QP 0 and BPG offset 2, max QP 8 produces byte `0x02`; max QP 4 produces `0x01`.

The source on-command table selects vendor page D2 at record 18, then contains 91 two-byte `0x15` writes at records 19–109. The blocks are identical in all four modes. Under the observed register/order-and-gap correspondence, 90 writes map to PPS bytes 0–93 (skipping identifier/reserved bytes 1, 2, 20, and 26); all 90 match the vendor PPS and 89 match mainline. Register `0x73 = 0x02` is the lone mismatch, corresponding to PPS byte 58. `0x97 = 0x08` is the one unmapped D2 write. The PPS bytes not covered by the correspondence are zero in the generated vendor PPS.

This supports the wording **“observed D2-to-PPS byte correspondence.”** It does not prove that page D2 is a PPS register bank: no RM692H5 register documentation or runtime readback establishes those semantics. The vendor also separately transmits a 128-byte PPS packet after the panel on-command sequence (`dsi_panel.c:5335-5375`; `dsi_display.c:9624-9644`). Whether the panel decodes D2 values, the received PPS, or both is unknown. The meaning of `0x97 = 0x08` and the skipped panel registers also remain unknown.

Therefore, `range_max_qp[0]` is the sole observed mismatch between the two generated PPS buffers and the sole mismatch in the 90 mapped D2 writes. It is a format/profile mismatch, not an established sole display blocker. If the panel uses the captured D2 value and the host path uses mainline's 4, the panel and encoder may disagree; no evidence here proves what the panel consumes or that changing it will produce an image.

## Mainline lifecycle and a panel-specific fixup

The same `drm_dsc_config` object can keep the panel PPS and DPU encoder in sync:

1. At MIPI-DSI attach, the MSM host stores `dsi->dsc` as `msm_host->dsc` (`dsi_host.c:1712-1731`).
2. During bridge pre-enable, the DSI manager powers the host (`dsi_manager.c:278-310`). `msm_dsi_host_power_on()` enables host supplies and link clocks, selects the active pin state, calls `dsi_timing_setup()`, then resets and enables the DSI controller (`dsi_host.c:2488-2535`). `dsi_timing_setup()` sets the active dimensions and calls `dsi_populate_dsc_params()` (`:996-1049`). That function overwrites the RC table with the generic pre-SCR VESA values (`:1878-1921`).
3. The panel bridge's pre-enable calls `drm_panel_prepare()` (`bridge/panel.c:113-130`). DRM normally visits downstream bridges before the host; setting `panel.prepare_prev_first = true` makes the previous DSI-host bridge run first (`drm_bridge.c:963-1029`, `bridge/panel.c:299-303`, `include/drm/drm_panel.h:262-269`). A command-sequenced panel needs this ordering so its prepare callback runs after host setup. The upstream Visionox RM692E5 driver is an API example: it sets that flag, assigns its panel-owned config to `dsi->dsc`, then packs and sends PPS in prepare (`panel-visionox-rm692e5.c:203-211,383-404`). It is a different panel and only a pattern reference.
4. The DPU gets the host's same config pointer through `msm_dsi_get_dsc_config()` / `msm_dsi_host_get_dsc_config()` (`dsi.c:15-18`, `dsi_host.c:2706-2710`; call site `dpu_encoder.c:639-653`) and retains it (`:1336-1345`). CRTC kickoff calls `dpu_encoder_prepare_for_kickoff()` (`dpu_crtc.c:1116-1118`), which programs DSC from that config (`dpu_encoder.c:2063-2103`); the hardware path reads `rc_range_params` directly (`dpu_hw_dsc_1_2.c:255-318`).

The smallest source-backed panel-specific option is to own one config in the NX809J panel driver, assign it to `dsi->dsc`, set `prepare_prev_first`, and apply the panel's RC override in `prepare()` **after** the host has populated the standard table and **before** sending D2 writes/PPS. Pack PPS from that same config pointer. For the observed vendor profile, the only necessary RC delta is `rc_range_params[0].range_max_qp = 8`; the remaining range entries already match. Since DPU kickoff later reads the shared pointer, the PPS and encoder receive the same value without changing the global VESA table or adding a generic option. The override must be re-applied after every host recomputation. This is a static integration proposal only; it has not been implemented.

## Remaining limits

- No packet acceptance, panel readback, DPU programming trace, visible output, TE test, reset test, or phone runtime test was performed. No kernel build was performed.
- TE is enabled by the vendor command sequence (`35 00`) and routed to captured TLMM 86 / `mdp_vsync`; actual TE edges, polarity, and synchronization remain unverified.
- Reset is TLMM 98, but the captured vendor consumer uses raw levels `1` for 10 ms, `0` for 10 ms, then `1` for 40 ms. The physical asserted polarity is unresolved. The panel rails are enabled sequentially: `vddio` 1.8 V, `vdd` 1.25 V, and `vci` 3.0 V with 2 ms delays; the `tvdd` supply link is unresolved. DSI controller and PHY supplies are separate. See [`docs/nx809j-panel.md`](nx809j-panel.md) and [`collab/results/T-011-panel-integration-map.md`](../collab/results/T-011-panel-integration-map.md).
- The 60-Hz mainline lane-rate estimate is about 847.5 Mbps/lane against a raw compressed active-payload lower bound of about 392 Mbps/lane. These are source/formula estimates, not measured clocks. The same static analysis puts 120 Hz near 8% raw-payload headroom and 144 Hz below the raw active-payload requirement. Link/PHY timing, panel acceptance, TE, and mode stability need hardware validation before adding higher refresh modes.

No display enablement, firmware execution, device access, or production source change was made.
